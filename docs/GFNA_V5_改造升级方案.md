> **项目**：`grna/` — GFNA 全球财经新闻聚合器 → 行情采集 + 量化选股系统
> **文档版本**：V5.1（历史深度定稿为 5 年）
> **编制日期**：2026-10-21
> **口径**：A 股（沪/深/北）· 近 5 年日线 · AKShare 主采集 · 零付费数据源
> **性质**：改造方案，暂不含代码实现

## 0. 结论摘要

| 维度 | 现状 | 判断 |
|---|---|---|
| 可运行性 | 虚拟环境缺 `asyncpg / akshare / yfinance / pandas / numpy` | **不可启动** |
| 个股级行情 | 0 张表，只有指数 / 板块 / 两融 | **完全缺失** |

一句话：**地基没浇完，演示层已经装修好了。** 改造不是推翻重写，而是把「行情 → 指标 → 因子 → 选股」这条主链补成真的，新闻链路降级为情绪因子输入。

## 1. 体检结论

### 1.1 项目现在跑不起来

实测 `pip list`，`asyncpg / akshare / yfinance / pandas / numpy` 全部缺失。后端 `create_async_engine("postgresql+asyncpg://…")` 在导入阶段就会失败，FastAPI 连启动都做不到。

`requirements.txt` 里 `yfinance==1.5.2` 这个版本号**存疑**（yfinance 长期在 0.2.x 系列，1.5.x 是否存在需联网核实 PyPI）。一个不存在的版本会让整条 `pip install` 失败，很可能是当初装不上的根因。

### 1.2 「量化选股」整层是假的

`westock-tool/scripts/index.js` 开头写着 `"Mock CLI"`，全文仅 117 行，核心是一个 `SAMPLE_DATA` 常量：

| 算法 | 硬编码条数 |
|---|---|
| A1 MACD 金叉 × 低估值 | 12 条 |
| A2 均线多头 × 主力加仓 | 5 条 |
| A3 央企 × 综合评分 | 5 条 |
| A4 高股息 × 低估值 | 8 条 |

数据抄自 `ROADMAP-V4.md` 里 2026-07-26 的样本。没有 fetch、没有请求、没有日期。算法中心展示的永远是同一批历史样本，与「当日行情」无关。

### 1.3 分析链路写得很完整，但多个环节恒定返回中性值

- 技术面需 30 天历史，板块表每天只插当天一行且**无历史回补** → 首月全部 5.0 分
- 论坛情绪 `hot_posts` 永远为 `None` → 5.0
- 板块资金流用 `df["名称"] == "BK1186"` 匹配中文名 → 永不命中 → 5.0

最终所有板块分数被拉到 5 分附近，排名失去意义。

## 4. 目标架构

**核心主张**：把「选股」从「调外部 CLI」改成「算本地数据」。

```
┌─ L1 采集层 ingest（新建）──────────────────────────────────┐
│  Provider 抽象 · akshare_em · baostock_fallback            │
│  交易日历 · 限频/重试/断点 · 幂等 upsert · 数据质量校验      │
└───────────────────────────┬────────────────────────────────┘
                            ▼
┌─ L2 存储层 PostgreSQL（扩展）──────────────────────────────┐
│  dim_stock · fact_stock_daily · fact_sector_daily          │
│  dim_sector_member · fact_moneyflow · fact_feature_daily   │
│  stg_run / stg_signal · meta_data_quality                  │
└───────────────────────────┬────────────────────────────────┘
                            ▼
┌─ L3 分析层 engine（重构）──────────────────────────────────┐
│  指标库 MA/RSI/MACD/BOLL/ATR                                │
│  因子库 价值/质量/动量/波动/流动性/情绪                     │
│  横截面 z-score · 综合评分                                  │
└───────────────────────────┬────────────────────────────────┘
                            ▼
┌─ L4 选股层 strategy（替换 mock）───────────────────────────┐
│  条件树引擎 · 内置策略 A1–A4 · 参数快照/run_id               │
│  回测（防未来函数）· 绩效指标                                │
└───────────────────────────┬────────────────────────────────┘
                            ▼
┌─ L5 服务与展示（改接口，前端小改）─────────────────────────┐
│  FastAPI /api/v1 · 数据新鲜度徽标 · React 看板 · 选股中心    │
└────────────────────────────────────────────────────────────┘
```

### 为什么不再调 westock-tool

1. 它是 mock，接真版本也无 SLA、5–30 秒响应、无回测能力；
2. 全市场日线落库后，选股本质是一次 SQL/DataFrame 运算，**毫秒级、可复现、参数真生效**；
3. 外部 CLI 无法回答「这个策略过去五年赚不赚钱」——而这恰恰是量化选股最该回答的问题。

**兼容做法**：保留 `algo_service` 对外函数签名（`list_algos` / `get_cached_result` / `run_algo`），只换内部实现，前端 `AlgoCenter.tsx` 几乎零改动。

## 5. 数据源选型

| 维度 | AKShare | Baostock | Tushare Pro | 腾讯/新浪 |
|---|---|---|---|---|
| 费用 | 免费 | 免费 | 积分制（部分付费） | 免费 |
| 全市场快照 | **支持**（一次拿全） | 不支持 | 支持（有权限门槛） | 支持（需逐只） |
| 历史日线 | 支持 | **支持且复权规范** | 最规范 | 有限 |
| 财务/估值 | 支持 | 部分 | **最全** | 仅实时字段 |
| 稳定性 | 中（依赖东财页面结构） | **高** | 高 | 中（非官方） |
| 维护频率 | 高频变动 | 低频 | 商业维护 | 随时可能变 |
| 合规性 | 二次封装，需自行限频 | 较友好 | 官方授权 | 非官方接口 |
| **结论** | **主源** | **兜底/校验** | 可选（升级财务因子时） | 备用（仅补实时） |

### 推荐组合

**AKShare 主采集 + Baostock 兜底校验 + 本地库为唯一事实源。**

三条原则：

1. **先落库再计算** —— 任何分析只读本地库，不在请求路径打外部接口，接口挂了也不影响看盘；
2. **Provider 抽象 + 降级链** —— 沿用「东财→同花顺」思路，扩成 `akshare → baostock → 缓存快照`；
3. **每个数据集都要有新鲜度元信息** —— 前端必须能显示「几点几分抓的、覆盖多少只」，否则无法判断信号可信度。

### 合规边界（写进代码注释与文档）

AKShare 本质是对公开页面的二次封装，不是交易所授权接口。落地须限频（全市场快照 ≤ 1 次/分钟、历史回补 ≤ 2 请求/秒）、固定 UA、遵守目标站点条款；**不实现任何绕过反爬、验证码识别、代理池轮换**。数据仅个人研究，不得对外分发或商用。

## 6. 数据模型改造

新增 7 张表，其中前 3 张是地基。

### 6.1 `dim_stock` 标的维度表

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | CHAR(6) PK | 6 位代码 |
| `exchange` / `board` | VARCHAR | SH/SZ/BJ；主板/创业板/科创板/北交所（涨跌停幅度不同，回测必须区分） |
| `name` / `industry_l1` / `industry_l2` | VARCHAR | 名称、申万一级/二级（行业中性化与集中度约束要用） |
| `ownership` | VARCHAR | 央企/地方国企/民企/外资 → 支撑 A3 策略 |
| `list_date` / `delist_date` | DATE | **退市标的必须保留**，否则回测有严重幸存者偏差 |
| `is_st` / `status` | BOOLEAN / SMALLINT | ST 标记（多数策略需剔除）、正常/停牌/退市 |
| `total_share` / `float_share` | NUMERIC | 总股本、流通股本 |
| `updated_at` | TIMESTAMPTZ | — |

### 6.2 `fact_stock_daily` 个股日线（核心）

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` + `trade_date` | 联合 PK | 按年分区（`PARTITION BY RANGE(trade_date)`），**5 年约 650 万行**（6 个年度分区 + 预建下一年 + default），分区后查询仍走索引 |
| `open/high/low/close` | NUMERIC(12,3) | 未复权原始价 |
| `pre_close` | NUMERIC(12,3) | 前收盘，判断涨跌停必需 |
| `pct_chg` / `amplitude` | NUMERIC(6,3) | 涨跌幅、振幅（%） |
| `volume` / `amount` | BIGINT / NUMERIC(20,2) | 成交量（股）、成交额（元），**两者严格区分，不能互相兜底** |
| `turnover_rate` | NUMERIC(8,4) | 换手率（%） |
| `adj_factor` | NUMERIC(12,6) | **复权因子——回测正确性全靠它**，缺了它所有收益率都是错的 |
| `market_cap` / `float_cap` | NUMERIC(20,2) | 总市值、流通市值 |
| `pe_ttm` / `pb` / `ps_ttm` / `dv_ttm` | NUMERIC | 估值快照（亏损股 PE 为负，筛选须显式处理） |
| `is_limit_up` / `is_limit_down` / `is_suspended` | BOOLEAN | **回测「不可成交」判定依据**，没有这三列的回测结果一律不可信 |
| `src` / `updated_at` | VARCHAR / TIMESTAMPTZ | 来源标识与更新时间，用于追溯 |

### 6.3 `dim_sector_member` 板块成分（带生效区间）

| 字段 | 类型 | 说明 |
|---|---|---|
| `sector_code` / `stock_code` | 联合 PK 之一 | 板块与成分股 |
| `effective_from` / `effective_to` | DATE | **SCD2 缓慢变化维**。成分会调整，只存「当前成分」会让回测用到未来信息 |

### 6.4 其余 4 张

| 表 | 优先级 | 用途 |
|---|---|---|
| `fact_feature_daily` | P1 | 预计算指标（MA/RSI/MACD/ATR/动量/波动/量比）。预计算而非查询时算，是全市场选股做到秒级的关键 |
| `fact_moneyflow` | P1 | 个股主力净流入 T0–T4、北向持股比例，A2 策略输入 |
| `stg_run` / `stg_signal` | P1 | 每次运行元信息（run_id、参数快照、数据版本、耗时）+ 信号明细。**没有 run 记录的策略结果不可复现** |
| `meta_data_quality` | P0 | 每个数据集最后成功时间、行数、覆盖率、异常数。**前端数据新鲜度的唯一来源** |

### 6.5 现有表处置

- `sector_daily` 保留，补「历史回补」
- `sector_score` 保留评分字段，**日报拆到独立 `daily_report` 表**（终止 `sector_code="__daily_report__"` 的 hack）
- `algo_results` 改为存策略输出快照（含 run_id），不再是「CLI 输出缓存」

## 9. 关键风险

| 风险 | 等级 | 应对 |
|---|---|---|
| AKShare 接口变动或被限流 | 高 | Provider 抽象 + 双源降级 + 本地库为唯一事实源；采集失败不影响已落库数据，前端显示新鲜度而非报错 |
| 首次全量回补耗时超预期 | 高 | 优先「按市场批量」而非逐只；分批 + 断点续传 + 夜间执行；先补 1 年打通，再异步补前 4 年 |
| 复权口径错误导致回测失真 | 高 | 强制存 `adj_factor`；用 Baostock 交叉校验 5–10 只样本；回测统一用「后复权价算收益」 |
| 未来函数 | 高 | 严格 T+1 成交；代码层禁止 `shift(-1)`；专门写未来函数检测用例 |
| 幸存者偏差（5 年窗口更突出） | 高 | `dim_stock` 保留退市标的与 `delist_date`；回测按「当日在市」过滤 |
| 数据量增长（5 年约 650 万行 / 2–2.5 GB） | 低 | PostgreSQL 分区 + 索引完全够用；按年分区，冷数据归档 |
| 合规边界 | 中 | 限频、固定 UA、遵守站点条款；不实现反爬绕过；仅个人研究 |

> **必须提前接受**：改造完成后得到的是「一套可信的数据与信号系统」，**不是「一套能稳定赚钱的策略」**。量化的价值在于把决策变得可复现、可归因、可证伪；回测好看的策略在实盘失效是常态。系统里必须常驻「数据新鲜度」与「回测≠实盘」两条警示。

## 10. 决策定稿与 5 年口径的补充影响

### 10.1 决策定稿

| 决策点 | 定稿 | 状态 | 理由 |
|---|---|---|---|
| ① 市场范围 | A 股（沪/深/北） | 默认 | 复用 AKShare 链路最省事；港股需另接代码体系与交易规则 |
| ② 历史深度 | **近 5 年** | **已调整** | 回测窗口需覆盖至少一轮完整牛熊，否则策略易被单一环境过拟合 |
| ③ 数据颗粒 | 仅日线 | 默认 | 分钟线是日线 240 倍数据量；选股以日频调仓为主 |
| ④ 数据源 | AKShare 主 + Baostock 兜底 | 默认 | 零预算下覆盖最全；Baostock 用于复权校验 |
| ⑤ 交付重心 | 先出信号 + 回测必做 | 默认 | 没有回测的信号无法判断有效性；组合优化后置阶段 6 |

### 10.2 5 年带来四个具体变化（不只是数字变大）

| 维度 | 3 年口径 | 5 年口径（定稿） | 要动的设计 |
|---|---|---|---|
| 数据量 | 约 400 万行 | **约 650 万行**（含退市标的可达约 730 万行） | 体积估算约 2–2.5 GB（含索引）。仍在单机 PostgreSQL 舒适区，但必须分区，不能一张大表裸跑 |
| 分区策略 | 3 个年度分区 | **6 个年度分区**（2021–2026 + 预建 2027 + default） | 建表时一次性预建；采集任务需带「自动建下一年分区」逻辑，否则跨年那天写入失败 |
| 回补耗时 | 首次 1–3 小时 | **首次 2–4 小时** | 请求次数不变（每只一次全历史），但单次返回体积更大、失败重拉成本更高；夜间执行 + 断点续传 + 失败清单重试 |
| 回测可信度 | 覆盖约 1 轮半周期 | **覆盖多轮极端环境** | 能穿过调整期与反弹期两类环境，策略在不同市况下的差异才能被看见——**这是上调到 5 年最实质的收益** |

### 10.3 5 年口径下新增的两条硬约束

1. **退市标的必须入库。** 窗口拉到 5 年，退市股数量显著增加。若只按「今天还在交易的股票」建池，回测会自动剔除所有后来退市的失败案例，收益率虚高——这是最典型的幸存者偏差。`dim_stock` 必须保留 `delist_date`，回测按「当日在市」过滤。

2. **复权因子必须按 5 年区间回溯。** 5 年内会发生多次送转与分红，若 `adj_factor` 起点取错，早期价格会被系统性放大或缩小，回测收益率直接失真。落地时用 Baostock 抽 5–10 只标的做交叉校验。

### 10.4 工时调整

- 阶段 1（数据地基）：4–6 人日 → **5–7 人日**（多出部分在分区预建、回补重试、复权校验）
- 整体：17–24 人日 → **18–26 人日**
- 阶段 0–2（出首个真实选股结果）：**10–14 人日**
- 其余阶段不变——分析层与策略层复杂度不随历史长度线性增长

### 10.5 建议的回补推进节奏

先回补最近 1 年打通「采集 → 落库 → 指标 → 选股」全链路（约 30–50 分钟），验证无误后再异步补齐前 4 年。这样阶段 1 的验收不必等到全量回补结束。
