01体检结论：先说实话

三句话概括——地基没浇完，演示层已经装修好了。
① 项目现在跑不起来。实测 .venv/Scripts/python.exe -m pip list， asyncpg / akshare / yfinance / pandas / numpy 全部缺失。 后端 create_async_engine("postgresql+asyncpg://…") 在导入阶段就会失败， FastAPI 连启动都做不到。requirements.txt 里 yfinance==1.5.2 这个版本号存疑（yfinance 长期在 0.2.x 系列，1.5.x 是否存在需联网核实），很可能是当初 pip install 失败的根因。
② 「量化选股」整层是假的。westock-tool/scripts/index.js 开头就写着 "Mock CLI"，文件里是 SAMPLE_DATA 常量： A1 仅 12 条、A2 仅 5 条、A3 仅 5 条、A4 仅 8 条，数据抄自 ROADMAP-V4 文档里 2026-07-26 的样本。 没有 fetch、没有请求、没有日期。所以算法中心展示的永远是同一批历史样本， 与「当日行情」毫无关系。
③ 分析链路写得很完整，但多个环节恒定返回中性值。 技术面需要 30 天历史，而板块表每天只插当天一行且无历史回补 → 首月全部 5.0 分； 论坛情绪 hot_posts 永远是 None → 5.0； 板块资金流用 df["名称"] == "BK1186" 匹配中文名 → 永不命中 → 5.0。 最终所有板块的分数被拉到 5 分附近，排名失去意义。

为什么不再调 westock-tool： ① 它是 mock，接真版本也无 SLA、5–30 秒响应、无回测能力； ② 一旦全市场日线落库，选股本质是一次 SQL/DataFrame 运算，毫秒级、可复现、参数真生效； ③ 外部 CLI 无法回答「这个策略过去三年赚不赚钱」，而这恰恰是量化选股最该回答的问题。
兼容做法：保留 algo_service 的对外函数签名（list / get_cached_result / run_algo）， 只把内部实现换成策略引擎 —— 前端 AlgoCenter.tsx 几乎零改动。

05数据源选型

这是整个方案最需要论证的一环：数据源决定系统能不能长期稳定跑。
候选对比 按「个人研究用途、零预算」前提评估
维度AKShareBaostock Tushare Pro腾讯 / 新浪行情
费用免费免费积分制（部分需付费）免费
全市场快照支持（一次拿全市场）不支持支持（有权限门槛）支持（需逐只/分批）
历史日线支持支持且复权规范最规范有限
财务 / 估值支持部分最全仅实时字段
稳定性中（依赖东财页面结构）高高中（非官方）
维护频率高频变动低频商业维护非官方，随时可能变
合规性二次封装，需自行限频较友好官方授权非官方接口
结论主源 覆盖全、快照一次到位 兜底 复权与历史校验 可选 财务因子升级时再接 备用 仅补实时
推荐组合：AKShare 主采集 + Baostock 兜底校验 + 本地库为唯一事实源。
关键原则三条：
① 先落库再计算——任何分析只读本地库，不在请求路径上打外部接口，这样接口挂了也不影响看盘；
② Provider 抽象 + 降级链——沿用现有「东财→同花顺」的思路，扩成 akshare → baostock → 缓存快照；
③ 每个数据集都要有「新鲜度」元信息——前端必须能显示「这份数据是几点几分抓的、覆盖多少只」，否则用户无法判断信号是否可信。
合规提示（必须写进代码注释与文档）：AKShare 本质是对公开页面的二次封装，不是交易所授权接口。 落地时须限频（建议全市场快照 ≤ 1 次/分钟、历史回补 ≤ 2 请求/秒）、固定 UA、遵守目标站点条款； 不实现任何绕过反爬、验证码识别、代理池轮换。数据仅用于个人研究，不得对外分发或商用。

09关键风险

风险等级应对
AKShare 接口变动或被限流高 Provider 抽象 + 双源降级 + 本地库为唯一事实源；采集失败不影响已落库数据的使用，前端显示新鲜度而非报错
首次全量回补耗时超预期高 优先用「按市场批量」接口而非逐只；分批 + 断点续传 + 夜间执行；先回补 1 年打通链路，再异步补齐前 4 年
复权口径错误导致回测失真高 强制存 adj_factor；用 Baostock 交叉校验 3–5 只样本的前复权价；回测统一用「后复权价算收益」
未来函数（用到当日收盘后才知道的信息）高 回测严格 T+1 成交；代码层面禁止 shift(-1)；专门写一条未来函数检测用例
幸存者偏差中 dim_stock 保留退市标的与 delist_date；回测时按当日「在市」过滤，而不是按今天的股票池
数据量增长（5 年约 650 万行 / 约 2–2.5 GB）低 PostgreSQL 分区 + 索引完全够用；按年分区，冷数据可归档
合规边界中 限频、固定 UA、遵守站点条款；不实现反爬绕过；数据仅个人研究，不对外分发
必须提前接受的一点：改造完成后，你得到的是「一套可信的数据与信号系统」，不是「一套能稳定赚钱的策略」。 量化选股的价值在于把决策变得可复现、可归因、可证伪；回测好看的策略在实盘失效是常态。 系统设计里必须始终保留「数据新鲜度」与「回测≠实盘」这两条警示。

10决策定稿与 5 年口径的补充影响

五个决策已定：市场范围/颗粒/数据源/交付重心取默认，历史深度上调为 5 年。以下把这一个变更带来的连锁影响补全。
决策定稿 已确认，可直接进入编码
决策点定稿状态理由
① 市场范围A 股（沪 / 深 / 北）默认 复用现有 AKShare 链路最省事；港股需另接代码体系与交易规则，收益不匹配成本
② 历史深度近 5 年已调整 回测窗口需覆盖至少一轮完整牛熊，否则策略容易被单一市场环境过拟合
③ 数据颗粒仅日线默认 分钟线是日线的 240 倍数据量，选股策略以日频调仓为主，无此必要
④ 数据源AKShare 主 + Baostock 兜底默认 零预算下覆盖最全；Baostock 用来交叉校验复权口径，不必付费
⑤ 交付重心先出信号 + 回测必做默认 没有回测的信号无法判断有效性；组合优化后置到阶段 6

回测可信度 覆盖约 1 轮半周期 覆盖多轮极端环境 5 年窗口能穿过调整期与反弹期两类环境，策略在不同市况下的表现差异才能被看见——这是上调到 5 年最实质的收益
5 年口径下新增的两条硬约束（务必写进开发清单）：
① 退市标的必须入库。窗口拉到 5 年，退市股数量显著增加。若只按「今天还在交易的股票」建池， 回测会自动剔除所有后来退市的失败案例，收益率虚高——这是最典型的幸存者偏差。 dim_stock 必须保留 delist_date，回测按「当日在市」过滤。
② 复权因子必须按 5 年区间回溯。5 年内会发生多次送转与分红，若 adj_factor 起点取错， 早期价格会被系统性放大或缩小，回测收益率直接失真。落地时用 Baostock 抽 5–10 只标的做交叉校验。
工时相应调整：阶段 1（数据地基）由 4–6 人日上调为 5–7 人日（多出的部分在分区预建、回补重试与复权校验）。
整体由 17–24 人日调整为 18–26 人日；其中阶段 0–2（能出第一份真实选股结果）约 10–14 人日。
其余阶段的估算不变——分析层与策略层的复杂度不随历史长度线性增长。
建议的回补推进节奏（避免一次性 4 小时卡住进度）： 先回补最近 1 年打通「采集 → 落库 → 指标 → 选股」全链路（约 30–50 分钟）， 验证无误后再异步补齐前 4 年。这样阶段 1 的验收不必等到全量回补结束。
核对方式：本方案中所有关于现状的判断均来自对工作区 grna/ 的实际读取与命令验证： 依赖缺失由 pip list 实测；mock 结论来自 westock-tool/scripts/index.js 源码； 其余条目均标注了文件与行号，可直接打开比对。
两处标注「需核实」：① yfinance==1.5.2 是否真实存在（当前环境无法联网核对 PyPI）； ② 全市场标的数量按约 5,400 只估算，实际以交易所披露为准。
